生成的 Protobuf 代码可以用两大风格之一来呈现消息（message）：

*   **开放式结构体 API（Open Struct API）**把消息的字段（field）公开为普通结构体的公有成员。用户代码直接读取、写入这些成员，并直接取其地址：`msg.foo = 42`、`*msg.foo`、`&msg.foo`。
*   **Opaque API** 把内存中的表示保持为私有，仅通过生成的方法来暴露消息：getter（读取器）、setter（设置器）、hazzer（存在性检查器）、clearer（清除器），以及某些语言中的构建器（builder）。

Protobuf 团队在每一种语言中都更青睐 Opaque API。开放式结构体看起来更简单，在某些语言里也显得更符合习惯用法，但它们把消息的物理内存布局提升成了公有 API，这会带来长期问题。

## 不透明性就是杠杆 {#leverage}

Protobuf 在两个方面不同寻常，而这两者都指向同一个方向。

其一，几乎一切事物都依赖 Protobuf，因此生成代码的*每一个*可观察行为，都在某处被某个人依赖着。这是 [Hyrum 定律](https://www.hyrumslaw.com/)体现得最淋漓尽致的地方：在实践中，凡是暴露出去的东西，我们就永远无法更改。

其二，Protobuf 位于整个服务机群的序列化（serialization）、远程过程调用（RPC）和存储层之下，因此即便是对解析（parse）或内存表示的微小改进，其总体影响也异常巨大。

综合来看，生成的 API 中暴露了过多细节，往往是我们让 Protobuf 更快、更小的能力所受到的最大单一约束。相比之下，我们发现不透明程度越高，能带来的杠杆效应就越大：它让我们能够更审慎地确定究竟哪些行为属于保证，也为在底层更换实现留出了空间。

## 不透明性带来的收益举例 {#what-it-buys}

当字段存储本身是公有 API 时，以下每一项要么无法实现，要么大打折扣。

### 缓存状态 {#cachedstate}

由于二进制线路格式（wire format）使用长度前缀，典型的序列化实现必须进行两趟处理：第一趟计算编码后的长度，第二趟再利用这些长度进行写入。

借助 Opaque API，你可以在内部维护一个缓存的编码长度，并在发生修改时使其失效。这为大幅加速序列化打开了大门。

使用开放式结构体则做不到：没有 setter，就无法"知道"可能改变编码长度的状态是否已被修改，这意味着每次序列化都必须重做大小计算工作。

### 惰性解码（lazy decoding） {#lazy}

借助 Opaque API，解码可以推迟到解析时刻之后进行。惰性子消息（submessage）字段、惰性扩展、惰性 UTF-8 校验等类似技术，全都是靠保留原始字节、并在首次访问时于 getter 内部完成实际工作来实现的。一个只读取少数几个顶层路由字段、其余内容原样转发的服务，根本不必为整个子树付出任何代价。

使用开放式结构体则做不到：普通的字段读取不是函数调用，因此不存在拦截点，解析器在构建消息树时也就别无选择，只能急切地把一切解析到位。

### 未装箱的值与密集 hasbits {#hasbits}

追踪[显式存在性（explicit presence）](/programming-guides/field_presence)要求为每个字段存储一位信息。Opaque API 存储的恰恰就是这一位：即内联字段值旁边、密集 `hasbits` 位向量中的一个位。

在没有零成本值可选性的语言中，开放式结构体做不到这一点，因为存在性位无法从字段表达式本身触达。典型的表示最终会变成每字段一个指针——`*int32`、`*bool`、`java.lang.Integer`——它在父结构体中占用一个机器字，需要一次独立的内存分配，每次读取都要多一次间接寻址，还带来垃圾回收器（garbage collector）压力，而这一切只是为了承载一个位。

即使在拥有 `Option<T>` 的 Rust 这类语言中，开放式 API 也让人无法在全部字段之上维护一个密集的 hasbit 位掩码，只能把可选性位分散到整个结构体中（而且通常每个字段还伴随着大量浪费性的填充）。

密集 hasbits 不仅存储起来更便宜，它们还让针对整条消息的操作变得更便宜，因为 `Clear()`、`ByteSizeLong()` 和 `MergeFrom()` 可以一次测试覆盖许多字段的掩码，并在完全不加载字段数据的情况下跳过它们。欲了解更多，请参阅[隐式存在性（implicit presence）](/design-decisions/implicit-presence#performance)。

### 更改内存布局的自由 {#layout}

当调用方无法依赖字段偏移量、也无法持有指向消息内部的指针时，运行时（runtime）便可以自由地重排消息：

*   **按访问模式布局。**频繁访问的字段可以一起放在第一个缓存行中，而很少被设置的字段则可以挪出去，放进一个只在其中某个字段被设置时才存在的溢出分配里。这些是随工作负载而定的决策，因此最好由性能剖析（profile）驱动，而不是在代码生成时固定下来。
*   **arena 与自定义内存分配。**消息的内部数据可以从连续的 arena 或内存块（slab）中分配；只有当没有任何调用方持有指向某个字段的裸指针——而该字段的生命周期即将被我们更改——时，这才是安全的。
*   **字符串与 bytes 的紧凑表示。**当每一次读取都经由访问器（accessor）居中处理时，内联小缓冲区、引用计数或共享切片、以及指向解析缓冲区的视图，就都成为可选项。

这些都不是一次性的收益。关键在于它们始终保持*可用*：未来的表示变更会以新运行时的形式发布，而不是变成对每个调用方的迁移。

## 案例研究：GoProto {#go}

Go 是最典型的例子：一门语言最初采用开放式结构体 API，后来转向了 Opaque API。

历史上，GoProto 生成的是公有结构体：其中显式存在性的标量（scalar）是指针（`*int32`、`*string`），而 proto3 隐式存在性的标量则是裸值。在 proto3 设计之时，开放式结构体被认为是打造高质量 Go 实现的一项必要条件。

实践证明恰恰相反：Go 的维护者发现，开放式结构体把他们困住了。字段无法重排，惰性解码无法实现，存在性也无法去装箱。

调用方还可能依赖生成的结构体本身，以至于在生成代码中加入一个未使用的零大小字段，就会弄坏数千个测试，这意味着即便是纯收益的变更，推行起来的代价也高得令人望而却步。

Go protobuf 的开发者曾强烈主张，没有开放式结构体就无法打造高质量、高效率的实现；他们后来推翻了这一决定，引入了访问器方法。他们意识到，使用开放式结构体会束缚自己的手脚，限制了所能实现的优化。有了开放式结构体，他们无法重排字段，也无法实现惰性解码。如果当初避开了开放式结构体，如今在如何优化方面本会拥有更多灵活性。

其成果就是 Go Opaque API：结构体字段是未导出的，访问一律通过 `Get*`、`Set*`、`Has*`、`Clear*` 以及构建器进行。它是[版次 2024（Edition 2024）](/editions/overview)及更新版次的默认选择，而且已公布的结果与上述推理相符：基本类型字段（elementary field）的存在性表示从每字段一个指针变为每字段一个位，参考基准测试中的内存分配次数分别下降了约 46% 和 58%，惰性解码基准测试节省了超过 50% 的工作量和超过 87% 的内存分配。详情请参阅 [Go Protobuf: The new Opaque API](https://go.dev/blog/protobuf-opaque)、[Go Opaque API 常见问题](/reference/go/opaque-faq)和 [Go Opaque API 迁移](/reference/go/opaque-migration)。

请注意，转向 Opaque API 是一次迁移，而非弃用（deprecation）：开放式结构体 API 仍会继续得到支持。

Go 并不是唯一的此类实验。`javanano`——一个面向 Android 的开放式结构体 Java 生成器——在 proto3 设计之时同样被认为很重要：它生成的消息是带有公有字段、没有构建器的可变对象。它同样被放弃，取而代之的是封装式的 `javalite` 运行时。两次相互独立的开放式结构体尝试，出现在两种截然不同的语言中，最终都以同样的方式收场。

## 不透明到何种程度才算够？ {#how-far}

更不透明总是意味着更多的实现自由，但它并非没有代价：超过某个程度之后，它就会损害目标语言惯用法的流畅性。这里存在真实的权衡，而我们是刻意为之的——按语言逐个决定，依据是究竟解锁了哪种能力。

Protobuf Rust 正是这一权衡当今的最前沿。符合惯用法的 Rust 会让子消息访问器返回 `&Foo` 和 `&mut Foo`，让字符串访问器返回 `&str`。而 Rust Protobuf 返回的却是视图（view）与可变（mut）*代理（proxy）*类型，即 `FooView<'_>` 和 `FooMut<'_>`，因为原生引用会强加两个我们无法满足的语言层不变量（invariant）：

*   **`&Foo` 要求在该地址的内存中确实存在一个真正的 Rust `Foo`。** Protobuf Rust 的一个核心目标，是以零成本的方式把 Rust 加入已经在使用 C++ Protobuf 的二进制程序——以普通指针的形式跨 FFI（外部函数接口）边界共享消息，而不是靠序列化跨边界传递。在这种设计下，已解析消息的子节点位于 C++ 堆上，没有可供借用的对应 Rust 对象；交出 `&Foo` 就意味着要急切地为每个子消息构造出一个镜像 Rust 结构体。这还会把内存表示固定下来，而这恰恰是我们想要保持自由的方面：Protobuf Rust 在同一套 API 之下支持多种具有不同布局的内核（kernel）。
*   **`&mut Foo` 可以被传入 `std::mem::swap`。**对分属不同父消息的两个子消息进行逐字节交换，无法修复其中的 arena 指针；更一般地说，它会剥夺我们维护父消息与其子节点之间任何不变量的能力。请注意，这个例子可能会在 Rust 即将到来的变更中得到修复，但时至今日依然如此：没有办法提供一个不能被 `swap` 作用到的 `&mut`。

代理类型让 Rust 调用方损失了一些熟悉感，这一点我们心中有数。我们之所以承担这一代价，是因为正是它让零拷贝（zero-copy）的 C++/Rust 互操作成为可能；任何更低程度的不透明性都做不到这一点。进一步的讨论请参阅 [Rust Proto 设计决策](/reference/rust/rust-design-decisions#view-mut-proxy-types)。

## 不透明性不是什么 {#what-it-is-not}

Opaque API 关乎的是隐藏*表示*，而不是隐藏数据或增加繁文缛节。具体而言：

*   访问器不是添加行为的邀请。getter 返回字段值，或在字段未设置时返回该字段的默认值（default value），参见[不支持可空 setter/getter](/design-decisions/nullable-getters-setters)。
*   不透明性不等于不可变性。消息是否可变，是一个独立的、按语言逐个决定的事项。
*   不透明性不是跳过反射（reflection）的理由。每种运行时都提供 Protobuf 反射；Opaque API 所消除的，是转而对字段使用*语言*反射的诱惑。
