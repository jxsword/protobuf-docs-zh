“1-1-1”最佳实践提倡这样的定义组织方式：每个 `.proto` 文件只保留一个顶层入口点——导出的消息（message）、导出的枚举（enum）、服务（service）或扩展（extension），并对应单一的 `proto_library` 构建规则。这种方式有助于形成小而模块化的 proto 定义。其主要收益包括：简化重构、有可能改善构建时间，以及因传递依赖（transitive dependencies）最小化而缩小二进制体积。

## 基本原理 {#rationale}

1-1-1 最佳实践要求让每个 `proto_library` 和 `.proto` 文件都尽可能保持在合理的小规模，理想的比例是：

*   一条 `proto_library` 构建规则
*   一个源 `.proto` 文件
*   一个顶层入口点（`export message`、`export enum`、`service` 或 `extend`）

在合理的前提下，导出的消息、枚举、扩展和服务的数量越少，重构就越容易。文件彼此分离之后，直接移动文件要比从同一个包含多个消息的文件中抽取消息容易得多。

遵循这一实践可以在实际中减小传递依赖的规模，从而有助于缩短构建时间、减小二进制体积：当某些代码只需要用到某一个枚举时，在 1-1-1 设计下，它可以只依赖定义该枚举的 `.proto` 文件，避免顺带引入一大组传递依赖——这些依赖可能只是同一文件中定义的另一个消息才会用到。

有些情况下，1-1-1 的理想状态无法实现（例如存在循环依赖（circular dependencies））、并不理想（例如概念上高度耦合的消息放在一起反而更有利于可读性），或者某些缺点并不适用（例如 `.proto` 文件没有任何导入（import）时，传递依赖的规模就不构成技术上的顾虑）。与任何最佳实践一样，何时偏离这条准则，需要你运用良好的判断力。

## 版次 2024 及更高版次中的符号可见性 {#2024-later}

从 `edition = "2024"` 开始，Protobuf 引入了[符号可见性](/programming-guides/symbol_visibility)机制，提供 `export` 与 `local` 关键字以及 `features.default_symbol_visibility` 选项。

> **范围说明：** 符号可见性**仅**控制 Protobuf 编译器（`protoc`）在解析 `.proto` 文件之间的引用时的导入行为。它对特定语言的生成代码（generated code）以及 proto 描述符（descriptor）的使用方**没有任何影响**。

### 推荐设置：`STRICT` {#strict}

对于版次（edition）2024 及更高版次的所有新 `.proto` 文件，文件选项 `features.default_symbol_visibility` 都应设置为 STRICT。这也是版次 2026 的默认值：

```proto
option features.default_symbol_visibility = STRICT;
```

在 `STRICT` 模式下：

*   所有符号默认为 `local`。
*   只有打算作为入口点的顶层 `message` 和 `enum` 声明才可以标记为 `export`。
*   嵌套符号不能使用 `export`，并且会被强制为 `local`（防止嵌套类型（nested type）被跨文件边界意外导入）。

顶层消息在设计上是复用场景下的**原子**单位。嵌套的消息和枚举天然只对其父容器私有。试图把另一个消息的嵌套类型当作可复用的词汇使用，会破坏 `.proto` 文件“要么全用、要么全不用”的设计。打算独立复用的类型，应当作为顶层符号定义在专门的 `.proto` 文件中。

### 针对 `local` 辅助符号的放宽 {#relaxation}

符号可见性机制对内部辅助符号放宽了严格的 1-1-1 要求：一个文件可以包含多个 `local message` 或 `local enum` 定义，前提是它们服务于同一个顶层入口点（即形成支持单一入口点的一个 `local` 符号簇）。由于 `local` 符号无法被其他 `.proto` 文件导入，它们不会给导入方造成传递依赖膨胀。

### 服务请求与响应消息 {#req-res}

在 2024 版次中，如果请求与响应消息被标记为 `local`（或在 `STRICT` 模式下默认为 `local`），那么把 `service` 与其请求/响应 `message` 放在同一个文件中是可以接受的。这样可以防止这些消息被导入其他 `.proto` 文件，也避免把 `service` 定义及其 gRPC 依赖拉入无关的构建目标。

但是，如果某个请求或响应消息将来需要在服务文件之外被共享或导入（例如用于日志记录、数据留存，或在另一个远程过程调用（RPC）中复用），就应当把它定义为独立的专属 `.proto` 文件中的顶层 `export message`。

## 模块化模式（schema）示例 {#example}

在创建 gRPC 定义时，proto 模式（schema）文件的模块化尤为重要。下面这组 proto 文件展示了 2024 版次下的模块化结构。

**student_id.proto**

```proto
edition = "2024";

package my.package;

option features.default_symbol_visibility = STRICT;

export message StudentId {
  string value = 1;
}
```

**full_name.proto**

```proto
edition = "2024";

package my.package;

option features.default_symbol_visibility = STRICT;

export message FullName {
  string family_name = 1;
  string given_name = 2;
}
```

**student.proto**

```proto
edition = "2024";

package my.package;

option features.default_symbol_visibility = STRICT;

import "student_id.proto";
import "full_name.proto";

export message Student {
  StudentId id = 1;
  FullName name = 2;
}
```

**get_student_request.proto**

```proto
edition = "2024";

package my.package;

option features.default_symbol_visibility = STRICT;

import "student_id.proto";
import "external/expensive/dependency.proto";

// 之所以导出并独立成文件，是因为它同时被
// student_request_log.proto 和 student_service.proto 使用。
export message GetStudentRequest {
  StudentId id = 1;
  expensive.external.OtherMessage message = 2;
}
```

**student_request_log.proto**

```proto
edition = "2024";

package my.package;

option features.default_symbol_visibility = STRICT;

import "get_student_request.proto";

// 记录发生的所有请求。
message StudentRequestLog {
  string requesting_user = 1;
  GetStudentRequest request = 2;
}
```

**student_service.proto**

```proto
edition = "2024";

package my.package;

option features.default_symbol_visibility = STRICT;

// 之所以要导入它，是因为 student_request_log.proto 中会记录这条消息，
// 这意味着该消息必须放在自己的文件中并使用 `export`。
import "get_student_request.proto";

local message GetStudentResponse {
  Student student = 1;
}

local message CreateStudentRequest {
  FullName name = 1;
}

local message CreateStudentResponse {
  Student student = 1;
}

service StudentService {
  rpc CreateStudent(CreateStudentRequest) returns (CreateStudentResponse);
  rpc GetStudent(GetStudentRequest) returns (GetStudentResponse);
}
```

服务定义及其 4 个消息定义中的 3 个都定义在 `student_service.proto` 中。这些消息全部标记为 `local`，因此可以安全地与 `service` 定义放在一起，而不会引入不必要的依赖。`GetStudentRequest` 由 `StudentService` 和 `StudentRequestLog` 共享，所以它应当放在自己的文件中。

在这个例子中，`Student`、`StudentId` 和 `FullName` 是公共领域类型，可以在日志、请求、响应以及外部 proto 中复用。

如果之后需要给 `FullName` 消息添加一个 `middle_name` 字段，你就无需在各个顶层消息中逐一添加这个新字段。同样，如果需要为 `Student` 补充更多信息，所有相关的请求和响应都会随之获得更新。此外，`StudentId` 也可能演化为多段式 ID。

最后，即便是 `StudentId` 这样简单的类型，将其封装为消息也意味着你创建了一个具有语义与集中文档的类型。对于 `FullName` 这类类型，你需要留意这些 PII（个人身份信息）会被记录到何处；这也是不在多个顶层消息中重复定义这些字段的另一个好处。你可以在一处将这些字段标记为敏感字段，并将其排除在日志之外。
