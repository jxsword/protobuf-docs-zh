以下各节介绍计划在 v30 发布（release）中实施的破坏性变更（breaking change）；v30 预计于 2025 年第一季度推出。这些内容描述的是我们预期的实现方式，但鉴于软件天然的灵活性，其中部分变更可能不会落地，也可能与本主题中的描述有所出入。

## C++ 中的变更 {#cpp}

C++ 的主版本（version）将从 5.29.x 提升到 6.30.x。

### 描述符 API {#descriptor-apis}

v30 将把描述符（descriptor）中的返回类型（例如 `full_name`）更新为 `absl::string_view`（字符串视图）。这将带来描述符内存占用上的节省。

v28 引入了 `PROTOBUF_FUTURE_STRING_VIEW_RETURN_TYPE` 宏。在该破坏性发布到来之前，你可以在此期间使用它来提前启用更新后的返回类型。v30 发布将翻转默认值并移除该宏。

### 从 FieldDescriptor 选项中移除 ctype {#ctype-removed}

v30 将停止从 `FieldDescriptor` 选项中暴露 `ctype`。你可以改用 [v28 发布](https://github.com/protocolbuffers/protobuf/releases/tag/v28.0)中新增的 `FieldDescriptor::cpp_string_type()` API 来替代。

### 用拉取的依赖替换 CMake 子模块 {#replace-cmake-submods}

v30 将移除子模块，并切换到 upb 旧有的 CMake 依赖拉取模式。

如果你使用的是已安装的软件包，则不会受到影响。但这可能破坏某些 CMake 工作流。

### 移除已弃用的 API {#remove-deprecated}

v30 将移除以下公共运行时 API。这些 API 至少已在一个次版本或主版本的发布周期中被标记为弃用（deprecated，例如通过 `ABSL_DEPRECATED`），且现已过时或已有替代。

### 停止支持 C++14 {#drop-cpp-14}

本次发布将不再把 C++ 14 作为最低支持版本，而是将其提升到 17，依据是[基础 C++ 支持矩阵（Foundational C++ Support matrix）](https://github.com/google/oss-policies-info/blob/main/foundational-cxx-support-matrix.md)。

按照[我们的政策](https://protobuf.dev/support/version-support/)，我们并不将此视为破坏性变更。

## JRuby 中的变更 {#jruby}

v30 将把 JRuby 的默认实现切换为 FFI，这对部分 JRuby 用户而言可能是破坏性的。

请注意，此变更不会带来 Ruby 主版本号升级，因为 JRuby [未受官方支持](/support/version-support/#ruby)。

## Python 中的变更 {#python}

Python 将把主版本从 5.29.x 提升到 6.30.x。

### 停止支持 Python 3.8

按照我们官方的 Python 支持政策，我们将停止支持 Python 3.8 及更低版本。这意味着最低支持的 Python 版本为 3.9。

### 移除 bazel/system_python.bzl 别名 {#python-remove-alias}

v30 将移除遗留的 `bazel/system_python.bzl` 别名。

请移除对 `system_python.bzl` 的直接引用，改用 `protobuf_deps.bzl`。如果确实需要直接引用，请使用 `python/dist/system_python.bzl`——它[在 v5.27.0 中](https://github.com/protocolbuffers/protobuf/commit/d7f032ad1596ceeabd45ca1354516c39b97b2551)被移动到了该位置。

### 字段设置器校验变更 {#python-setter-validation}

v30 将修复 Python 与 upb 的字段设置器，使之校验版次（edition）2023 下的封闭式枚举（closed enum）。使用无效值更新的封闭式枚举字段将产生错误。

## Objective-C 中的变更 {#objc}

**这将是 Objective-C 的首个破坏性发布**。

Objective-C 将把主版本从 3.x.x 提升到 4.30.x。

### 全面改造未知字段处理 API 并弃用大部分现有 API {#objc-field-handling}

v30 将弃用 `GPBUnknownFieldSet` 并以 `GPBUnknownFields` 取而代之。新类型会保留未知字段（unknown fields）在原始输入或 API 调用中的顺序，从而在消息（message）写回时保住顺序所承载的语义。

作为其中一部分，`GPBUnknownField` 类型的 API 也有变动：几乎所有现有 API 都转为弃用，同时新增了一批新 API。

已弃用的属性 API：

*   `varintList`
*   `fixed32List`
*   `fixed64List`
*   `lengthDelimitedList`
*   `groupList`

已弃用的修改操作 API：

*   `addVarint:`
*   `addFixed32:`
*   `addFixed64:`
*   `addLengthDelimited:`
*   `addGroup:`

已弃用的初始化方法 `initWithNumber:.`

新增的属性 API：

*   `type`
*   `varint`
*   `fixed32`
*   `fixed64`
*   `lengthDelimited`
*   `group`

该类型会在其值中建模单个字段编号（field number），而不是针对给定的字段编号把所有值*分组*在一起。用于创建新字段的 API 是 `GPBUnknownFields` 类上的各个 `add*` API。

v30 还将弃用 `-[GPBMessage unknownFields]`。作为替代，将提供新的 API 来提取和更新消息的未知字段。

## 其他变更 {#non-breaking}

除上述破坏性变更之外，还有一些值得注意的其他变更。以下变更虽不被视为破坏性变更，但仍可能对用户产生影响。

### 毒丸警告 {#poison}

v30 将更新毒丸（poison pill）机制，针对旧生成代码与新运行时的组合发出警告——这类组合在新的滚动升级策略下可以工作，但在*下一次*主版本提升时会中断。例如，Java 4.x.x 生成代码应能与 5.x.x 运行时搭配工作，但面对 6.x.x 运行时会发出即将中断的警告。

### C# 与 Ruby 中 UTF-8 强制校验的变更 {#utf-8-enforcement}

v30 将包含一项修复，使 UTF-8 强制校验在各语言之间保持一致。在字符串字段中存有非法非 UTF-8 数据的用户，可能会更早看到暴露出来的 UTF-8 强制校验错误。
