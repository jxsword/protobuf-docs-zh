以下各节介绍 v38 发布（release）中额外计划实施的破坏性变更（breaking change），v38 预计于 2027 年第一季度发布。这些内容描述了我们所预期的变更实现方式，但由于软件本身具有灵活性，其中部分变更可能不会最终落地，或与本主题中的描述有所出入。

## C++ 的变更 {#cpp}

### 移除描述符名称中的 NULL 终止符

返回 `absl::string_view` 的描述符（descriptor）API 将不再保证以 null 结尾。移除这些 null 终止符是为了在描述符中节省内存。

此变更适用于返回 `absl::string_view` 的描述符方法。调用方不得假定 `.data()` 返回的指针以 null 结尾。如果需要以 null 结尾的 C 风格字符串，调用方应显式构造 `std::string`（例如 `std::string(desc->name())`），或迁移到直接接受 `absl::string_view` 的 API。

## Protoc 的变更 {#protoc}

### 禁止在 `--descriptor_set_in` 中出现冲突的描述符

当通过 `--descriptor_set_in` 提供相互冲突的文件描述符时，Protoc 将报错。

Protoc 此前已引入在跨输入集合检测到冲突描述符时发出警告的机制。在 v38 发布中，该警告将升级为错误。构建系统和调用方必须确保输入到 `--descriptor_set_in` 的描述符集合不会为同一个 .proto 文件（proto file）提供相互冲突的定义。

## Python 的变更 {#python}

### 在纯 Python 实现上将 `Any` 字段的 `__eq__()` 对齐 Py-upb 行为

纯 PythonProto 的 `__eq__()` 行为将与 upb 对齐：仅比较序列化后的字节。在某些边界情况下，两个 `Any` 字段可能包含不同的字节，这些字节只有在解析之后才相等。此类情况过去返回 `true`，但现在将返回 `false`。

## UPB 的变更 {#upb}

### 使默认值中 float 与 double 的格式化对齐 C++ `FileDescriptor::CopyTo`

在 `upb_FileDef_ToProto` 中，`FieldDescriptorProto.default_value` 里的 `float` 与 `double` 默认值（default value）此前使用硬编码的 `"%.9g"` 和 `"%.17g"` 进行格式化。这产生的数字位数可能多于 C++ 的 `FieldDescriptor::DefaultValueAsString()`（`io::SimpleFtoa` / `io::SimpleDtoa`），导致 `upb_FileDef_ToProto` 的输出与 C++ 的 `FileDescriptor::CopyTo` 不一致（例如对于 `double` 会出现 `"0.10000000000000001"` 与 `"0.1"` 的差异，对于 `float` 会出现 `"7.77777779e+35"` 与 `"7.777778e+35"` 的差异）。

在 v38 中，`upb_FileDef_ToProto` 将使用与 `io::SimpleFtoa` 和 `io::SimpleDtoa` 一致的往返（round-trip）格式化来格式化 `float` 与 `double` 默认值。
