以下公告专门针对 30.x 版本（version），该版本于 2025 年 3 月 4 日发布（release）。按时间顺序呈现的信息请参阅
[新闻](/news)。

以下章节介绍 v30 发布中计划进行的破坏性变更（breaking change），预计于 2025 年第一季度发布。其中还包含一些并非破坏性、但可能需要你采取行动的变更。这些内容描述的是我们预计的实施方式，但由于软件固有的灵活性，其中部分变更可能最终不会落地，也可能与本文中的描述有所不同。

## C++ 的变更 {#cpp}

C++ 将把主版本号从 5.29.x 升级到 6.30.x。

### 描述符（descriptor）API {#descriptor-apis}

v30 将把描述符中的返回类型（例如 `full_name`）更新为 `absl::string_view`。这将为描述符带来内存节省。

v28 引入了 `PROTOBUF_FUTURE_STRING_VIEW_RETURN_TYPE` 宏，在此期间你可以使用它，在破坏性发布到来之前启用更新后的返回类型。v30 发布将翻转默认值并移除该宏。

### 从 FieldDescriptor 选项中移除 ctype {#ctype-removed}

v30 将不再从 `FieldDescriptor` 选项中暴露 `ctype`。你可以改用 `FieldDescriptor::cpp_string_type()` API，它是在 [v28 发布](https://github.com/protocolbuffers/protobuf/releases/tag/v28.0)中加入的。

### 将 CMake 子模块替换为拉取的依赖 {#replace-cmake-submods}

v30 将移除子模块，并切换到 upb 旧的 CMake 依赖拉取模式。

如果你使用的是已安装的软件包，则不会受到影响。但这可能破坏某些 CMake 工作流。

### 修改调试 API 以脱敏（redact）敏感字段 {#debug-redaction}

我们计划在 v30 中修改 Protobuf 调试 API（包括 Protobuf AbslStringify、`proto2::ShortFormat`、`proto2::Utf8Format`、`Message::DebugString`、`Message::ShortDebugString`、`Message::Utf8DebugString`），对标注了 `debug_redact` 的敏感字段（field）进行脱敏；这些 API 的输出将包含一个随进程而异的随机前缀，因此将无法再被 Protobuf TextFormat 解析器解析。

更多信息请参阅[2024 年 11 月 21 日发布的新闻文章](/news/2024-11-21)。

### 移除一个与反射（reflection）相关的函数 {#removing-mutable-repeated}

我们将移除以下与反射相关的函数：`MutableRepeatedFieldRef<T>::Reserve()`。

即将在 [`RepeatedPtrField`](/reference/cpp/api-docs/google.protobuf.repeated_field#RepeatedPtrField) 中推出的一项性能改进与此 API 不兼容。该改进预计将加速对 `RepeatedPtrField` 元素的重复访问，尤其是顺序访问。

### 移除已弃用（deprecated）的 API {#remove-deprecated}

v30 将移除以下公共运行时（runtime）API：它们已被标记为弃用（deprecated，例如通过 `ABSL_DEPRECATED`）至少一个次版本或主版本，且已过时或已有替代品。

### 停止支持 C++14 {#drop-cpp-14}

本次发布将不再以 C++ 14 作为最低支持版本，而是将其提升至 17，依据是[基础 C++ 支持矩阵（Foundational C++ Support matrix）](https://github.com/google/oss-policies-info/blob/main/foundational-cxx-support-matrix.md)。

按照[我们的政策](https://protobuf.dev/support/version-support)，我们不认为这是破坏性变更。

### 在 Arena 上清空 oneof 消息后引入 ASAN 毒化

此变更增加了一项加固检查，影响使用 Arena 的 C++ Protobuf 消息（message）。在 Protobuf arena 上分配的 oneof 消息现在会在调试模式下被清空，并在 ASAN 模式下被毒化。调用 clear 之后，后续任何使用该内存区域的行为都会以释放后使用（use-after-free）错误的形式在 ASAN 中引发崩溃。

此实现需要 C++17。

### 停止提供 C++ CocoaPods 发布

在 v30 中，我们将停止提供自 v4.x.x 起就已损坏的 C++ CocoaPods 发布。C++ 用户应改用我们的 [GitHub 发布页](https://github.com/protocolbuffers/protobuf/releases)。

## JRuby 的变更 {#jruby}

v30 会将 JRuby 的默认实现切换为 FFI，这对某些 JRuby 用户而言可能是破坏性的。

请注意，此变更不会带来 Ruby 主版本号升级，因为 JRuby [不受官方支持](/support/version-support/#ruby)。

## Python 的变更 {#python}

Python 将把主版本号从 5.29.x 升级到 6.30.x。

### 停止支持 Python 3.8

按照我们的官方 Python 支持政策，我们将停止支持 Python 3.8 及更低版本。这意味着受支持的最低 Python 版本为 3.9。

### 移除 bazel/system_python.bzl 别名 {#python-remove-alias}

v30 将移除旧的 `bazel/system_python.bzl` 别名。

请移除对 `system_python.bzl` 的直接引用，改用 `protobuf_deps.bzl`。如果需要直接引用，请使用 `python/dist/system_python.bzl`，它是在 [v5.27.0](https://github.com/protocolbuffers/protobuf/commit/d7f032ad1596ceeabd45ca1354516c39b97b2551) 中被移动到该位置的。

### 字段设置器验证的变更 {#python-setter-validation}

Python 与 upb 的字段设置器将在 v30 中修复，以验证版次 2023（edition 2023）下的封闭式枚举（closed enum）。以无效值更新封闭式枚举字段将产生错误。

### 移除已弃用的 py_proto_library 宏

`protobuf.bzl` 中已弃用的内部 `py_proto_library` Bazel 宏将在 v30.x 中被移除。

它应替换为官方的 `py_proto_library`；自 v29.x 起，该宏将被移入 Protobuf 的 `bazel/py_proto_library`。在 v29.x 之前，此实现可在 `rules_python` 中找到。

### Python 针对映射字段的 setdefault 行为变更

从 v30 开始，对于 `ScalarMap`，`setdefault` 的行为将类似于 `dict`，区别在于键（key）和值（value）都必须设置。对 `MessageMaps` 使用 `setdefault` 将被拒绝。

## Python 嵌套消息类 \_\_qualname\_\_ 包含外层消息名称

Python 嵌套消息类的 `__qualname__` 现在包含外层消息的名称。在 v30 之前，对于嵌套消息，`__qualname__` 的结果与 `__name__` 相同，即其中不包含外层消息名称。

例如：

```python
message Foo {
  message Bar {
    bool bool_field = 1;
  }
}
nested = test_pb2.Foo.Bar()
self.assertEqual('Bar', nested.__class__.__name__)
self.assertEqual('Foo.Bar', nested.__class__.__qualname__) # 之前为 'Bar'
```

## Objective-C 的变更 {#objc}

**这将是 Objective-C 的第一个破坏性发布**。

Objective-C 将把主版本号从 3.x.x 升级到 4.30.x。

### 全面修订未知字段处理 API，弃用现有大多数 API {#objc-field-handling}

v30 将弃用 `GPBUnknownFieldSet`，并以 `GPBUnknownFields` 取而代之。新类型会保留未知字段（unknown fields）相对于原始输入或 API 调用的顺序，以确保消息写回时顺序所承载的任何语义都得以维持。

作为此变更的一部分，`GPBUnknownField` 类型的 API 也有所改动：现有 API 几乎全部被标记为弃用，同时新增了新的 API。

已弃用的属性 API：

*   `varintList`
*   `fixed32List`
*   `fixed64List`
*   `lengthDelimitedList`
*   `groupList`

已弃用的修改 API：

*   `addVarint:`
*   `addFixed32:`
*   `addFixed64:`
*   `addLengthDelimited:`
*   `addGroup:`

已弃用的初始化方法 `initWithNumber:`。

新的属性 API：

*   `type`
*   `varint`
*   `fixed32`
*   `fixed64`
*   `lengthDelimited`
*   `group`

此类型的值对应单个字段编号（field number），而不是把给定字段编号的所有值*归组*在一起。用于创建新字段的 API 是 `GPBUnknownFields` 类上的 `add*` API。

v30 还将弃用 `-[GPBMessage unknownFields]`。作为替代，将提供新的 API 来提取和更新消息的未知字段。

## 其他变更 {#other}

### 毒化 MSVC + Bazel

我们将在 v34 中停止支持 Bazel 与 MSVC 搭配使用。从 v30 起，我们会以报错形式毒化（poison）这一组合，除非你指定选择退出标志 `--define=protobuf_allow_msvc=true` 将其静默。

MSVC 的路径长度限制与 Bazel 的沙箱机制相叠加，使得同时支持两者变得越来越困难。与其让把 Protobuf 安装到长路径下的用户随机遭遇故障，我们将全面禁止在 Bazel 中使用 MSVC。我们将继续通过 CMake 支持 MSVC，并开始通过 Bazel 支持 [clang-cl](https://clang.llvm.org/docs/UsersManual.html#clang-cl)。如需反馈或讨论，请访问 https://github.com/protocolbuffers/protobuf/issues/20085。

## 其他变更（非破坏性） {#non-breaking}

除上述破坏性变更之外，还有一些值得注意的其他变更。以下变更虽不被视为破坏性变更，但仍可能对用户产生影响。

### 毒丸（poison pill）警告 {#poison}

v30 将更新毒丸机制，为旧生成代码与新运行时的组合发出警告——这些组合在新的滚动升级政策下可以工作，但在*下一个*主版本升级时会失效。例如，Java 4.x.x 生成代码应当可以配合 5.x.x 运行时工作，但配合 6.x.x 运行时时会就即将到来的失效发出警告。

### C# 与 Ruby 中 UTF-8 强制校验的变更 {#utf-8-enforcement}

v30 包含一项修复，使各语言的 UTF-8 强制校验保持一致。字符串字段中含有非 UTF8 坏数据的用户，可能会更早看到被暴露出来的 UTF-8 强制校验错误。

### Ruby 与 PHP 在 JSON 解析中的报错

v30 依据 [JSON 规范](https://protobuf.dev/programming-guides/json/)修复了数值字段中字符串的 JSON 解析不符合规范的问题。

此修复不会伴随主版本号升级，但 Ruby 和 PHP 现在会对数值字段中的非数字字符串（例如 ""、"12abc"、"abc"）抛出错误。v29.x 会为这些错误情形包含一条警告。
