<p><code>#include &lt;google/protobuf/io/coded_stream.h&gt;<br>namespace <a href="#google.protobuf.io">google::protobuf::io</a></code></p><p>本文件包含 <a href='#CodedInputStream'>CodedInputStream</a> 和 <a href='#CodedOutputStream'>CodedOutputStream</a> 两个类，它们分别包装一个 <a href='google.protobuf.io.zero_copy_stream#ZeroCopyInputStream'>ZeroCopyInputStream</a> 或 <a href='google.protobuf.io.zero_copy_stream#ZeroCopyOutputStream'>ZeroCopyOutputStream</a>，让你能够以各种格式读取或写入单个数据片段。 </p><p>其中特别实现了整数的 varint 编码——一种简单的可变长度编码，数值越小占用的字节越少。</p>

<p>通常，这些类只会在 Protobuf 库内部用于编码和解码 Protobuf 消息（message）。库的使用者只有在希望编写自定义的消息解析或序列化（serialization）过程时，才需要了解这些类。</p>

<p><a href='#CodedOutputStream'>CodedOutputStream</a> 示例：</p>

<pre>// 向 "myfile" 写入一些数据。首先写入一个 4 字节的"魔数"（magic number）
// 以标识文件类型，然后写入一个长度限定（length-delimited）字符串。该
// 字符串由一个给出长度的 varint 后跟原始字节组成。
//
int fd = open("myfile", O_CREAT | O_WRONLY);
ZeroCopyOutputStream* raw_output = new FileOutputStream(fd);
CodedOutputStream* coded_output = new CodedOutputStream(raw_output);

int magic_number = 1234;
char text[] = "Hello world!";
coded_output-&gt;WriteLittleEndian32(magic_number);
coded_output-&gt;WriteVarint32(strlen(text));
coded_output-&gt;WriteRaw(text, strlen(text));

delete coded_output;
delete raw_output;
close(fd);</pre>

<p><a href='#CodedInputStream'>CodedInputStream</a> 示例：</p>

<pre>// 读取上面代码创建的文件。
int fd = open("myfile", O_RDONLY);
ZeroCopyInputStream* raw_input = new FileInputStream(fd);
CodedInputStream* coded_input = new CodedInputStream(raw_input);

coded_input-&gt;ReadLittleEndian32(&amp;magic_number);
if (magic_number != 1234) {
  cerr &lt;&lt; "File not in expected format." &lt;&lt; endl;
  return;
}

uint32 size;
coded_input-&gt;ReadVarint32(&amp;size);

char* text = new char[size + 1];
coded_input-&gt;ReadRaw(buffer, size);
text[size] = '\0';

delete coded_input;
delete raw_input;
close(fd);

cout &lt;&lt; "Text is: " &lt;&lt; text &lt;&lt; endl;
delete [] text;</pre>

<p>有兴趣的话，varint 编码的定义如下：</p>

<p>这种编码作用于最长 64 位的无符号整数。编码值的每个字节具有如下格式：</p>

<ul>
  <li>第 0-6 位：被编码数字的 7 个位。</li>
  <li>第 7 位：如果这是编码中的最后一个字节则为 0（此时数字剩余的位全为 0），如果后面还有更多字节则为 1。第一个字节包含数字中最低的 7 个有效位，第二个字节（如果存在）包含次低的 7 个位，依此类推。因此，二进制数 1011000101011 会被编码为两个字节 "10101011 00101100"。</li>
</ul>

<p>理论上，varint 可用于编码任意长度的整数。但出于实用性考虑，我们把上限设为 64 位。因此一个数字编码后的最大长度为 10 字节。 </p>

<p>假设你正在把一条消息解析进消息对象 m，并想利用 <a href='#CodedInputStream.SetExtensionRegistry'>SetExtensionRegistry()</a>。你必须遵守以下要求：</p>
<p>给定的 <a href='google.protobuf.descriptor#DescriptorPool'>DescriptorPool</a> 必须包含 m-&gt;GetDescriptor()。仅仅包含一个名称和内容都相同的描述符是不够的——它必须是<i>同一个对象</i>。换言之： </p>
<pre>assert(pool-&gt;FindMessageTypeByName(m-&gt;GetDescriptor()-&gt;full_name()) ==
       m-&gt;GetDescriptor());</pre>
<p> 有两种方式可以满足此要求：1) 使用 m-&gt;GetDescriptor()-&gt;pool() 作为池。这通常没什么用 </p>
<pre>因为即使你完全不调用
，最终使用的也会是这个池。</pre>
<p> 2) 使用一个 <a href='google.protobuf.descriptor#DescriptorPool'>DescriptorPool</a>，它把 m-&gt;GetDescriptor()-&gt;pool() 作为</p>
<pre>（即"底层池"）。 更多有关底层池的信息，请阅读
DescriptorPool 的文档。</pre>
<p>你还必须提供一个 <a href='google.protobuf.message#MessageFactory'>MessageFactory</a>。该工厂将用于构造表示扩展的 <a href='google.protobuf.message#Message'>Message</a> 对象。对于通过所提供的池可以找到的任何 <a href='google.protobuf.descriptor#Descriptor'>Descriptor</a>，该工厂的 GetPrototype() 都必须返回非 NULL。</p>
<p>如果所提供的工厂可能返回协议编译器生成（即编译进程序）的类型的实例，或者外层消息对象 m 是生成类型，那么给定的工厂必须具有如下性质：如果传给 GetPrototype() 的 <a href='google.protobuf.descriptor#Descriptor'>Descriptor</a> 位于 <a href='google.protobuf.descriptor#DescriptorPool.generated_pool'>DescriptorPool::generated_pool()</a> 中，则工厂必须返回与 <a href='google.protobuf.message#MessageFactory.generated_factory'>MessageFactory::generated_factory()</a> 相同的原型。也就是说，给定生成类型的描述符时，工厂必须返回生成类的实例（而不是 DynamicMessage）。而当给定的描述符所对应的类型不在 generated_pool 中时，工厂可以自由返回任何实现。</p>
<p>这条要求的原因是：生成的子对象可能通过标准的——而非反射（reflection）的——扩展访问器（accessor）方法访问，而这些方法会把对象向下转换为生成类的类型。如果对象实际上不是该类型，结果将是未定义的。另一方面，如果某个扩展没有编译进程序，代码就不可能通过标准访问器访问它——访问该扩展的唯一途径是反射。使用反射时，DynamicMessage 与生成消息无法区分，因此这些对象用 DynamicMessage 表示也没有问题。</p>
<p>使用一个已调用过 SetDelegateToGeneratedFactory(true) 的 <a href='google.protobuf.dynamic_message#DynamicMessageFactory'>DynamicMessageFactory</a> 即可满足上述要求。</p>
<p>pool 和 factory 如果有一个为 NULL，则两者都必须为 NULL。</p>
<p>注意，解析"lite"消息时会忽略此特性，因为它们没有描述符。 </p>

</div><h2 id="CodedOutputStream">class CodedOutputStream</h2><p><code>#include &lt;<a href="#">google/protobuf/io/coded_stream.h</a>&gt;<br>namespace <a href="#google.protobuf.io">google::protobuf::io</a></code></p><p>编码并写入二进制数据的类，这些数据由 varint 编码的整数和定宽片段组成。 </p><p>包装了一个 <a href='google.protobuf.io.zero_copy_stream#ZeroCopyOutputStream'>ZeroCopyOutputStream</a>。大多数用户不需要直接接触 <a href='#CodedOutputStream'>CodedOutputStream</a>。</p>
<p>在 <a href='#CodedOutputStream'>CodedOutputStream</a> 中，大多数返回 bool 的方法会在底层发生 I/O 错误时返回 false。一旦发生这种失败，<a href='#CodedOutputStream'>CodedOutputStream</a> 即已损坏，不再可用。Write* 方法不返回流状态，但发生错误时会使流失效。客户端可以通过探测 <a href='#CodedOutputStream.HadError'>HadError()</a> 来确定状态。</p>
<p>注意，<a href='#CodedOutputStream'>CodedOutputStream</a> 中每个写入数据的方法都有对应的静态 "ToArray" 版本。这些版本直接写入提供的缓冲区，并返回指向最后一个写入字节之后的指针。它们要求缓冲区具有足以容纳编码数据的容量。这使得一种优化成为可能：在开始写入之前先检查输出流是否有足够空间容纳整条消息，如果有，则只调用 ToArray 方法，从而避免对每个单独的值做边界检查。例如上面的示例中：</p>
<pre>CodedOutputStream* coded_output = new CodedOutputStream(raw_output);
int magic_number = 1234;
char text[] = "Hello world!";

int coded_size = sizeof(magic_number) +
                 CodedOutputStream::VarintSize32(strlen(text)) +
                 strlen(text);

uint8* buffer =
    coded_output-&gt;GetDirectBufferForNBytesAndAdvance(coded_size);
if (buffer != nullptr) {
  // 输出流在缓冲区中有足够空间：直接写入
  // 该数组。
  buffer = CodedOutputStream::WriteLittleEndian32ToArray(magic_number,
                                                         buffer);
  buffer = CodedOutputStream::WriteVarint32ToArray(strlen(text), buffer);
  buffer = CodedOutputStream::WriteRawToArray(text, strlen(text), buffer);
} else {
  // 进行带边界检查的写入，它会按需向底层流
  // 请求更多空间。
  coded_output-&gt;WriteLittleEndian32(magic_number);

</div> <hr><h3 id="CodedOutputStream.SetSerializationDeterministic.details"><code>void CodedOutputStream::SetSerializationDeterministic(<br>&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;bool value)</code></h3><div style="margin-left: 16px"><p>告知序列化器用户是否需要确定性序列化。 </p><p>未调用此方法时的默认值来自全局默认设置，由 SetDefaultSerializationDeterministic 控制。</p>
<p>确定性序列化的具体含义完全取决于序列化过程的驱动者（即 WriteVarint32 等方法的调用者）。对于使用 <a href='google.protobuf.message_lite#MessageLite'>MessageLite</a> 的方法之一来序列化 Protobuf 消息的情形，这意味着对于给定的二进制程序，相等的消息总是序列化为相同的字节。具体而言：</p>
<pre>对同一消息的重复序列化会返回相同的字节。

运行同一二进制程序的不同进程（包括在不同
机器上）会把相等的消息序列化为相同的字节。</pre>
<p>注意，这<i>并未</i> 跨语言通用的规范化（canonical）形式。由于未知字段（unknown fields）的存在，在消息定义发生变更的不同构建之间，它也不稳定。需要规范化序列化的用户（例如以规范形式持久存储、计算指纹）应当定义自己的规范化规范，并使用反射 API 实现序列化器，而不是依赖此 API。 </p>
