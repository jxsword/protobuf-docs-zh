<p><code>#include &lt;google/protobuf/descriptor.h&gt;<br>namespace <a href="#google.protobuf">google::protobuf</a></code></p><p>本文件包含用于描述协议消息（message）类型的类。 </p><p>你可以利用消息的描述符（descriptor）在运行时了解该消息包含哪些字段（field），以及这些字段分别是什么类型。<a href='google.protobuf.message#Message'>Message</a> 接口还允许你动态访问和修改各个字段，只需传入你所关注字段的 <a href='#FieldDescriptor'>FieldDescriptor</a>。</p>

<p>大多数用户并不需要关心描述符（descriptor），因为他们会针对特定的协议类型编写代码，直接使用协议编译器生成的类即可。想要操作任意类型（编译期未知）的高级用户，可能需要读取描述符来了解消息（message）的内容及其包含的字段（field）。只有极少数用户会想要构建自己的 Descriptor，原因或者是他们在自行实现 <a href='google.protobuf.message#Message'>Message</a>，或者是因为他们在编写类似协议编译器这样的工具。</p>

<p>至于如何使用描述符的示例，可参见 <a href='google.protobuf.message'>message.h</a> 顶部的代码示例。</p>

</div><h2 id="DescriptorPool">class DescriptorPool</h2><p><code>#include &lt;<a href="#">google/protobuf/descriptor.h</a>&gt;<br>namespace <a href="#google.protobuf">google::protobuf</a></code></p><p>用于构建描述符。 </p><p>通常你不会想要构建自己的描述符。协议编译器所构建的 <a href='google.protobuf.message#Message'>Message</a> 类会替你提供描述符。不过，如果你要自行实现 <a href='google.protobuf.message#Message'>Message</a>，或者你要编写一个能够处理完全任意类型、并需要从某种数据库加载这些类型的程序，那么你可能就需要自己动手了。</p>
<p>由于描述符由大量相互交叉关联的数据组成，手动组装会非常麻烦，因此提供了 <a href='#DescriptorPool'>DescriptorPool</a> 类来简化这一过程。它可以接收 FileDescriptorProto（定义于 descriptor.proto 中），对其进行验证，并将其转换为一组相互良好关联的 Descriptor。</p>
<p><a href='#DescriptorPool'>DescriptorPool</a> 还有助于内存管理。描述符由许多包含静态数据且相互持有指针的对象组成。到了需要删除这些数据的时候，你多半希望一次性全部删除。事实上，存在一整个相互交叉关联、并希望一次性删除的描述符池的情况并不少见。此类就表示这样的一个池，并替你处理内存管理。</p>
<p>你也可以在某个 <a href='#DescriptorPool'>DescriptorPool</a> 中按名称搜索描述符，并按编号搜索扩展。 </p>

</div> <hr><h3 id="DescriptorPool.DescriptorPool.details"><code>explicit  DescriptorPool::DescriptorPool(<br>&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;const <a href='#DescriptorPool'>DescriptorPool</a> * underlay)</code></h3><div style="margin-left: 16px"><p>创建一个叠加在其他池之上的 <a href='#DescriptorPool'>DescriptorPool</a>。 </p><p>如果在叠加池中搜索某个描述符而没有找到，就会退而搜索底层池。如果底层池还有自己的底层池，则继续搜索，依此类推。这也意味着，在叠加池中构建的文件会视需要与底层池的描述符交叉关联。底层池仍归调用者所有；它必须在新构建的池的生命周期内保持有效。</p>
<p>示例：假设你想在运行时解析一个 .proto 文件，以便将它的类型与 DynamicMessage 一起使用。再假设这个 .proto 文件有依赖项，但你知道所有依赖都已经是编译进二进制文件的东西。为了方便起见，你希望直接从 <a href='#DescriptorPool.generated_pool'>generated_pool()</a> 加载这些类型，而不必在运行时解析所有这些 .proto 文件的冗余副本。但是，你又不想把解析出来的类型直接加入 <a href='#DescriptorPool.generated_pool'>generated_pool()</a>：这是不允许的，而且无论如何都是糟糕的设计。因此，你可以改为把 <a href='#DescriptorPool.generated_pool'>generated_pool()</a> 用作新 <a href='#DescriptorPool'>DescriptorPool</a> 的底层池，并在其中只添加新文件。</p>
<p>警告：使用底层池可能带来许多隐蔽的陷阱。请尝试改用 DescriptorDatabase 来表述你想做的事情。 </p>
</div> <hr><h3 id="DescriptorPool.InternalSetLazilyBuildDependencies.details"><code>void DescriptorPool::InternalSetLazilyBuildDependencies()</code></h3><div style="margin-left: 16px"><p>仅供内部使用：启用文件依赖的惰性构建。 </p><p>把文件描述符依赖的构建推迟到绝对必要时才进行，例如对定义在该依赖文件中的字段调用 message_type() 时。如果某个 proto 或其依赖之一存在错误，这会导致功能问题。只应为 generated_pool_（因为编译生成过程保证不会出现描述符构建错误）、测试，或者能够保证某个池不出现描述符构建错误的情形启用此功能。 </p>
