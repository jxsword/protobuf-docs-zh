<p><code>#include &lt;google/protobuf/message.h&gt;<br>namespace <a href="#google.protobuf">google::protobuf</a></code></p><p>定义 <a href="#Message">Message</a>，即由非 lite 协议消息（message）对象实现的抽象接口。 </p><p>尽管可以手动实现该接口，但大多数用户会使用协议编译器来生成实现。</p>

<p>使用示例：</p>

<p>假设你有一个如下定义的消息（message）：</p>

<pre>message Foo {
  optional string text = 1;
  repeated int32 numbers = 2;
}</pre>

<p>然后，如果你使用协议编译器根据上面的定义生成了一个类，就可以像下面这样使用它：</p>

<pre>std::string data;  // 将保存该消息的一个序列化（serialization）版本。

{
  // 创建一个消息并将其序列化。
  Foo foo;
  foo.set_text("Hello World!");
  foo.add_numbers(1);
  foo.add_numbers(5);
  foo.add_numbers(42);

  foo.SerializeToString(&amp;data);
}

{
  // 解析序列化后的消息，并检查其中
  // 包含的数据是否正确。
  Foo foo;
  foo.ParseFromString(data);

  assert(foo.text() == "Hello World!");
  assert(foo.numbers_size() == 3);
  assert(foo.numbers(0) == 1);
  assert(foo.numbers(1) == 5);
  assert(foo.numbers(2) == 42);
}

{
  // 与上一个代码块相同，但改用 Message 的
  // 反射（reflection）接口以动态方式完成。
  Message* foo = new Foo;
  const Descriptor* descriptor = foo-&gt;GetDescriptor();

  // 获取我们所关注字段（field）的描述符（descriptor），
  // 并验证其类型。
  const FieldDescriptor* text_field = descriptor-&gt;FindFieldByName("text");
  assert(text_field != nullptr);
  assert(text_field-&gt;type() == FieldDescriptor::TYPE_STRING);
  assert(text_field-&gt;label() == FieldDescriptor::LABEL_OPTIONAL);
  const FieldDescriptor* numbers_field = descriptor-&gt;
                                         FindFieldByName("numbers");
  assert(numbers_field != nullptr);
  assert(numbers_field-&gt;type() == FieldDescriptor::TYPE_INT32);
  assert(numbers_field-&gt;label() == FieldDescriptor::LABEL_REPEATED);

  // 解析消息。
  foo-&gt;ParseFromString(data);

  // 使用反射接口检查其内容。
  const Reflection* reflection = foo-&gt;GetReflection();
  assert(reflection-&gt;GetString(*foo, text_field) == "Hello World!");
  assert(reflection-&gt;FieldSize(*foo, numbers_field) == 3);
  assert(reflection-&gt;GetRepeatedInt32(*foo, numbers_field, 0) == 1);
  assert(reflection-&gt;GetRepeatedInt32(*foo, numbers_field, 1) == 5);
  assert(reflection-&gt;GetRepeatedInt32(*foo, numbers_field, 2) == 42);

  delete foo;
}</pre>

<p>这将确保以下查找能够成功：</p>
<pre>DescriptorPool::generated_pool()-&gt;FindMessageTypeByName("FooMessage");</pre>
<p>作为副作用，它还将保证来自同一 .proto 文件的其他所有内容也可在生成池中查找。</p>
<p>此函数并不会真正注册该消息，因此无需在查找之前调用。不过，它必须位于一个不会从二进制文件中被剔除的函数内（即必须能从 main 到达）。</p>
<p>最佳实践是尽可能在接近实际需要反射的位置调用此函数。此函数的调用开销极低，因此除了最紧凑的循环之外，你无需担心其运行时（runtime）开销（在 x86-64 上它会编译为两条 "mov" 指令）。 </p>

</div><h2 id="Reflection">class Reflection</h2><p><code>#include &lt;<a href="#">google/protobuf/message.h</a>&gt;<br>namespace <a href="#google.protobuf">google::protobuf</a></code></p><p>此接口包含可用于动态访问和修改协议消息各字段的方法。 </p><p>它们的语义与协议编译器生成的访问器（accessor）类似。</p>
<p>要获取 <a href='#Reflection'>Reflection</a>（针对给定的 <a href='#Message'>Message</a>），请调用 <a href='#Message.GetReflection'>Message::GetReflection()</a>。</p>
<p>出于效率方面的考虑，此接口才与 <a href='#Message'>Message</a> 分开；<a href='#Message'>Message</a> 的绝大多数实现都会共享同一个 <a href='#Reflection'>Reflection</a> 实现（GeneratedMessageReflection，定义于 generated_message.h），而且某个特定类的所有 Message 都应共享同一个 <a href='#Reflection'>Reflection</a> 对象（不过你不应依赖后一点）。</p>
<p>这些方法存在若干种误用方式。例如，出现以下任一情况都会导致未定义的结果（很可能是断言失败）：</p>
<ul>
  <li><a href='google.protobuf.descriptor#FieldDescriptor'>FieldDescriptor</a> 不是此消息类型的字段。</li>
  <li>所调用的方法与字段的类型不匹配。对于 FieldDescriptor::TYPE_* 中的每种字段类型，只有一个对该类型有效的 Get*() 方法、一个 Set*() 方法和一个 Add*() 方法。应当选用哪个方法是显而易见的（TYPE_BYTES 可能除外，它在 C++ 中以字符串表示）。</li>
  <li>针对单数字段（singular field）的 Get*() 或 Set*() 方法被用于了可重复字段。</li>
  <li>GetRepeated*()、SetRepeated*() 或 Add*() 被用于了非可重复字段。</li>
  <li>传给任何方法的 <a href='#Message'>Message</a> 对象与此 <a href='#Reflection'>Reflection</a> 对象的类型不匹配（即 message.GetReflection() != reflection）。</li>
</ul>
<p>你可能想知道，为什么没有任何针对任意类型字段的抽象表示。例如，为什么不干脆提供一个返回 "const Field&amp;" 的 "GetField()" 方法，其中 "Field" 是某个带有 "GetInt32Value()" 等访问器的类。问题在于，必须有人来负责分配这些 Field 对象。对于生成消息类而言，为包装每个字段而额外分配一个对象的空间，至少会使消息的内存占用翻倍，甚至更糟。而按需分配这些对象则代价高昂且容易内存泄漏。因此，我们最终采用了这种扁平的接口。 </p>

        field-&gt;number(), new_value);
